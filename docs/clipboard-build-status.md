# Точка продолжения: файловый буфер Aspia 2.7

Сохранено 17 октября 2026, около 20:04 UTC (18 октября, 01:04 Екатеринбург).

## Цель и границы

Windows: Ctrl+C/Ctrl+V файлов и папок в обе стороны, новые Host, Client и Console на базе 2.7.0. Существующие Router/Relay и рабочие Host не обновлять. Результат пока только приватный черновик предварительного релиза. Старые 2.7 должны сохранять обычные подключения, текстовый буфер и прежнюю передачу файлов.

Вся работа сохранена в `denisvosk/aspia`, ветка `feature/clipboard-files-2.7`, [draft PR #1](https://github.com/denisvosk/aspia/pull/1). Код и CI на момент этой записи: `121f006f8eb572cd546d60b19d35a51e314de6d0`. Исходная 2.7.0: `488a77e13dc0c0ee07e4a6838e6ae400ae0c1c7f`; оригинальная резервная ветка сохранена. Не заменять main до проверки.

## Сделано, но Windows ещё не подтверждён

- Реализованы протокол файлового буфера поверх существующего ClipboardEvent и Windows OLE IDataObject/IStream, интеграция Host/Client/Console, согласование поддержки и проверка прав. Основные файлы: `source/common/clipboard_file_transfer.*`, `clipboard_files_win.*`, `source/proto/clipboard_file.proto`.
- Добавлены проверки путей, размеров, индексов, адресации сеансов, отмены и ограничений потоков. Исправлено время жизни уведомлений ClipboardMonitor.
- Добавлены тесты протокола, фильтра ввода и Windows OLE. Linux-проверка протокола **прошла**, включая 9 тестов: [run 39064823080](https://github.com/denisvosk/aspia/actions/runs/39064823080). Windows OLE ещё не собран и не проверен.
- Подготовлены Windows CI x86/x64 и упаковка Host/Client/Console MSI 2.7.1 с исходными UpgradeCode, проверкой содержимого MSI и пробным обновлением исходного Host 2.7.0 в изолированном runner. Результаты этих Windows-проверок ещё неизвестны.
- Подготовлено сохранение MSI, исходников, лицензии и SHA256 в приватный draft prerelease. Actions artifacts не используются: их хранилище у владельца было заполнено. Автообновление рабочих машин не настраивалось.
- Исправлена проверка настройки отключения автообновлений Host, чтобы тестовая установка могла сохранять собственную сборку.

## Сборки на момент записи

1. [Windows run #5, 39064171580](https://github.com/denisvosk/aspia/actions/runs/39064171580), job `117488191020`, `windows-x86`: выполняет `Configure and build dependencies`. Это более ранний снимок кода. **Не отменять во время первой сборки зависимостей**: Qt собирается долго. После конфигурации отдельный шаг сохраняет бинарный кэш до сборки самой Aspia.
2. [Windows run #8, 39064823035](https://github.com/denisvosk/aspia/actions/runs/39064823035): ожидает предыдущую сборку; уже содержит последние изменения и матрицу x86/x64. Сохранение этой записи может создать новый ожидающий run и заменить #8. Ориентироваться на самый новый run ветки и SHA его checkout.
3. `cancel-in-progress: false`: активная сборка продолжает работу независимо от чата. В группе GitHub сохраняет только последний ожидающий запуск. После завершения #5 новый запуск начнётся автоматически при доступном runner/лимите аккаунта.

**Готовых новых MSI на момент записи нет. Нельзя объявлять сборку или ручную проверку успешной.**

## Уже устранённые препятствия CI

- MSVC action перезаписывал VCPKG_ROOT: переменная восстанавливается в шаге конфигурации.
- Используется исходный toolset v142, собственные release-only triplets `ci/triplets` и фиксированный vcpkg4aspia `7eb700c9688daed6d8bdcdc571ebe3eedea6a774`.
- Устаревшие MSYS2 URL давали 404. `ci/vcpkg-tools/vcpkg_acquire_msys.cmake` сохраняет совместимую старую реализацию функции с новым каталогом пакетов из microsoft/vcpkg `2200159cd465157f20133e363e4604ac4d68181b`. Версии библиотек Aspia не обновлялись.
- pkg-config обеспечивается pkgconfiglite 0.28.0 и PKG_CONFIG.
- Старый upstream `sw.yml` в этой ветке переведён на ручной запуск; новый workflow отменяет только его оставшиеся запуски этой ветки.

## Что делать при продолжении

1. Проверить последний Windows run ветки и #5. Логи незавершённого job через GitHub API могут возвращать 404: это не означает ошибку сборки.
2. После завершения открыть логи, исправить конкретные ошибки MSVC, тестов или WiX и сохранить изменения в эту же ветку. Не пересобирать зависимости без необходимости; кэш архитектур раздельный. Не включать платный бюджет без разрешения.
3. Дождаться успешных сборки, ctest, упаковки и проверки обновления Host для обеих архитектур. Последний run должен собирать последний код, а не ранний снимок #5.
4. Проверить приватный draft release `v2.7.1-clipboard-preview.<run_number>`: шесть MSI, исходники, LICENSE, инструкции, SHA256 для обеих архитектур. Частичная загрузка одним matrix job ещё не означает полный готовый релиз.
5. Затем дать владельцу ссылку на черновик и провести ручную проверку двух Windows-машин по `docs/clipboard-preview.md`. Проверки через настоящий Router/Relay, Explorer, отмены и совместимости со старой 2.7 пока не выполнены.

Известные ограничения: копирование без удаления исходника, до 4096 элементов, ограничение длины относительного пути, без junction/симлинков/ACL/ADS, 30 секунд ожидания блока. Подробности и сценарии проверки — в `docs/clipboard-preview.md`.
