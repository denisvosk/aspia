# Aspia 2.7.1: экспериментальный файловый буфер Windows

Это частная доработка Aspia 2.7.0 (исходный тег 488a77e13dc0c0ee07e4a6838e6ae400ae0c1c7f), а не официальный релиз автора Aspia. Лицензия GPLv3 или более поздняя сохранена. Новые файлы и изменения помечены как community continuation (2026).

## Что изменено

Host, Client и Console поддерживают копирование файлов и папок через буфер Windows: Ctrl+C в Проводнике на одной машине, Ctrl+V в Проводнике или на рабочем столе другой. Обе стороны должны использовать эту сборку. В настройках сеанса должен быть включён буфер обмена; учётная запись Host должна иметь права управления рабочим столом и передачи файлов. В режиме просмотра файловый буфер недоступен.

В новой preview добавлен расширенный буфер Windows: обычный текст, RTF, полный HTML-буфер и PNG с совместимым DIB-представлением. Несколько форматов записываются одной подборкой. Это перенос подхода из Aspia 3.1.1, адаптированный к протоколу 2.7; код и проверки отличаются. Возможность согласуется отдельно от передачи файлов: при подключении к старой 2.7 передаётся обычный текст. Для форматированного текста и картинок достаточно разрешённого буфера в сеансе управления; право передачи файлов требуется только файловому буферу.

RTF сохраняет встроенные изображения вместе с текстом. Если HTML того же фрагмента содержит тег картинки, а RTF содержит встроенное изображение, используется RTF: Word может сохранять в HTML ссылки на временные файлы, недоступные другой машине. Полный CF_HTML сохраняет стили из заголовка документа. При вставке в Word выберите «Сохранить исходное форматирование». Отсутствующие шрифты, связанные внешние изображения и встроенные OLE-объекты не гарантируют идентичного результата; полноценный буфер Excel с формулами пока не реализован.

Используются существующий зашифрованный транспорт 2.7, ClipboardEvent и FilePacketizer. Поддержка согласовывается отдельным флагом. Исходные номера полей протокола, Router и Relay не менялись. Старые компоненты 2.7 продолжают использовать прежний текстовый буфер и отдельное окно передачи файлов.

Файлы читаются по запросу вставки, блоками до 256 КиБ. Передаются только элементы текущей скопированной подборки. Запрос не может содержать произвольный путь на исходном компьютере. Внутренний идентификатор получателя назначает служба Host из аутентифицированного сеанса. Ограничены размеры сообщений, количество файлов и одновременных потоков. Разрыв сеанса или смена подборки прекращает незавершённые потоки. Исправлено время жизни отложенных уведомлений ClipboardMonitor при закрытии сеанса. Служба Host теперь учитывает настройку отключения автоматического обновления: в исходной 2.7 её обработчики не проверяли этот флаг.

## Ограничения предварительной сборки

- Windows, пакеты x86 и x86_64. Приложения x86 работают и на 64-разрядной Windows. Для обновления Host используйте ту же архитектуру, которая уже установлена: x86 → x86, x86_64 → x86_64.
- Поддерживается копирование, не перемещение: Ctrl+X не удаляет исходник на удалённой машине.
- До 4096 элементов в одной подборке. Относительное имя должно помещаться в FILEDESCRIPTOR Windows; для первого варианта ограничено также 259 байтами UTF-8. Ссылки и junction не обходятся. Недопустимая подборка не передаётся; используйте обычную передачу файлов.
- Переносятся содержимое и структура папок. ACL, альтернативные потоки NTFS и временные метки не переносятся.
- Ожидание следующего блока ограничено 30 секундами. После отмены/ошибки повторите Ctrl+C. Медленный канал делят изображение рабочего стола и файлы; отдельного ускоренного канала пока нет.
- Буфер Windows общий для сеансов одного пользователя. Несколько окон удалённого доступа могут менять текущую подборку, как и обычные приложения Windows.
- Для расширенного содержимого лимит одной подборки — 16 МиБ до сжатия и 4 МиБ в транспортном сообщении; RTF/HTML/PNG сжимаются ZSTD, когда это уменьшает размер. При превышении используется обычный текст, если он есть; большая отдельная картинка не передаётся. Изображение ограничено 64 МиБ распакованных пикселей. Эти лимиты не относятся к файлам, которые передаются потоково. Разбиение богатого буфера на сетевые блоки пока не добавлено: крупная подборка может кратковременно занять общий канал.
- При незавершённой вставке Windows может оставить частичный файл в папке назначения. Ошибка возвращается Проводнику; такой файл нужно удалить или заменить повторной вставкой.
- MSI не подписаны сертификатом автора. Это тестовая сборка. Новые MSI допускают замену предыдущей preview поверх установленной 2.7.1. Номер 2.7.1 одинаков у нескольких сборок: выбирайте нужную preview по её выпуску и SHA256; возможна и установка более старой preview поверх новой.

## Проверка перед использованием

Не обновляйте сразу рабочие Host. Используйте две тестовые Windows-машины и сохраните установщики 2.7.0, адресную книгу Console и конфигурацию Host (`C:\ProgramData\aspia\host.json`). Конфигурация содержит секреты: храните резервную копию приватно.

1. Установите Host на тестовую машину, Client или Console — на вторую. На тестовом Host отключите автоматическое обновление, чтобы он не заменил доработанную сборку релизом из другого источника. Проверьте подключение через существующие Router/Relay 2.7.
2. Скопируйте и вставьте файл в обе стороны. Затем проверьте несколько файлов, кириллицу, вложенные и пустые папки, файл нулевого размера, файл больше 1 ГБ. Сравните SHA256 исходника и результата.
3. Проверьте отмену вставки, разрыв связи, закрытие окна, новую подборку во время вставки, блокировку/разблокировку Windows и повторное подключение.
   При передаче большого файла и папки проверьте также индикатор и возможность перемещать/использовать окно Проводника назначения. Для расширенного буфера скопируйте в обе стороны фрагмент Word с разными шрифтами, таблицей и встроенной картинкой, затем снимок экрана в Paint/Word и обычный текст в Блокнот.
4. Отключите буфер обмена; убедитесь, что файловый буфер перестал работать. Проверьте пользователя без права передачи файлов, режим просмотра и два одновременных клиента.
5. Проверьте новый Client с исходным Host 2.7.0 и исходный Client с новым Host: рабочий стол, текст и прежняя передача файлов должны работать.
6. На отдельной тестовой машине проверьте обновление Host той же разрядности 2.7.0 → 2.7.1: служба запускается, ID, Router, учётные записи и настройки сохранились. Не кладите рядом с MSI файл `aspia-host-config.json`: штатный установщик импортирует его.

Автотесты протокола и OLE запускаются в GitHub Actions. Извлечение MSI сверяет упакованные EXE/DLL с результатом сборки. В изолированной машине CI дополнительно проверяется установка исходного Host каждой разрядности 2.7.0, обновление до 2.7.1, запуск службы и сохранение тестовой конфигурации. Эти проверки не заменяют интерактивную проверку двух машин и реального обновления установленного Host. Пока она не завершена, релиз остаётся черновиком и не размещается на сервере автообновлений.

## Сборка и исходники

CI собирает x86 и x86_64. О наличии конкретной архитектуры судите по файлам MSI в черновике релиза; для обновления установленного Host разрядность должна совпадать.

Сборка описана в `.github/workflows/clipboard-windows.yml`: MSVC v142, CMake 3.28.4, WiX 3, vcpkg4aspia 7eb700c9688daed6d8bdcdc571ebe3eedea6a774, статические зависимости x86/x64 Release. Для удалённых пакетов инструментов MSYS2 сохранён обновлённый каталог URL/SHA512 из microsoft/vcpkg@2200159cd465157f20133e363e4604ac4d68181b; версии библиотек Aspia не обновляются. Workflow собирает и проверяет исходники, создаёт шесть MSI с оригинальными UpgradeCode и языковыми ресурсами, затем сохраняет исходники и SHA256 в приватный черновик релиза. Запуск: изменение `ci/build-request.txt` в PR либо workflow_dispatch, когда workflow доступен в основной ветке.

При передаче изменённых MSI другим людям предоставляйте соответствующие исходники этой же сборки, LICENSE.md и сведения об изменениях. Исходники включены в тот же релиз. Перед дальнейшим распространением отдельно учтите лицензии статически включённых библиотек.


## Follow-up to preview.17

Host file clipboard now belongs to the interactive user process instead of the
SYSTEM desktop agent. This targets the live FILECONTENTS 0x80040064 failure.
The user has confirmed file and folder paste in both directions with this fix.
MSIs permit replacement of the earlier 2.7.1 preview; Host CI verifies both the
original 2.7.0 upgrade and preview.17 replacement, including installed file hashes.
Use the intended new preview; the displayed 2.7.1 version alone does not identify it.

## Explorer responsiveness follow-up

The working build still blocks the destination Explorer window during paste;
individual files show a legacy progress dialog, folders do not. This follow-up
enables IDataObjectAsyncCapability so Shell can extract data on a background
thread, and requests FD_PROGRESSUI for directory descriptors as well as files.
The existing STA COM marshaling and 2.7 network protocol remain in use.
Windows tests cover async negotiation, cross-process background folder-child
reads, cancellation and repaste. Live Explorer responsiveness/progress still
needs checking after the new build; see clipboard-live-test-status.md.
