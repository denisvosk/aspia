# Aspia+ — фокус и раскладка ввода через вложенные сеансы

**Статус: исследование и проект, НЕ реализовано.** 2026-11-23.

> **Решение по приоритетам от 2026-11-23 (обязательное ограничение).**
> Стабильность Windows Host, Client и Console важнее удобства Android-клавиатуры.
> **Нельзя вносить рискованные изменения в настольные компоненты ради мобильной
> синхронизации раскладки.** Обновление Host/Console ради этой возможности
> НЕ запланировано и не требуется; описанная далее архитектура — только
> техническая возможность на будущее, а не утверждённая задача релиза.
> При недостаточной изоляции, отсутствии независимых тестов или заметном
> риске регрессии от функции следует отказаться.
>
> **Приемлемое рабочее решение уже есть:** с телефона пользователь видит
> индикатор языка на удалённой Windows и вручную переключает раскладку
> курсором/нажатием в её панели задач. Вложенные Aspia остаются штатным
> сценарием, но автоматическая синхронизация языка не обязательна.
>
> Мобильный клиент может независимо улучшать геометрию клавиатуры,
> доставку физических скан-кодов и удобство ввода; он не должен тайно
> посылать Alt+Shift / Win+Space при свайпе пробела. Если сведения о
> фактической раскладке недоступны, нельзя выдавать локальный выбор
> RU/EN за подтверждённый язык конечной Windows.
>
> Любая последующая идея Host/Console расширения: только отдельная
> экспериментальная ветка, за feature flag, выключенная по умолчанию,
> совместимая со стандартными рабочими сеансами, с проверками
> многоуровневого ввода и возможностью безболезненного отката.


## Практический вариант без обновления Host — переключение клавишами с телефона (включая Linux)

**Новый приоритет:** пробовать только клиентский механизм, не трогая
стабильные Windows Host, Client и Console. Свайп по пробелу может
**по выбору пользователя** отправлять одну заранее настроенную комбинацию
физических клавиш в текущий удалённый сеанс. Это best-effort, не
«установить RU/EN» и не подтверждение фактической раскладки.

- Значение по умолчанию **«только смена подписей мобильной клавиатуры,
  без удалённого переключения»**. Опционально для конкретного компьютера:
  **Alt+Shift**, **Ctrl+Shift**, **Win+Space**, **Super+Space**, либо
  пользовательская комбинация в пределах безопасного набора.
- Windows: Win+Space официально поддерживается; Ctrl+Shift работает при
  соответствующей конфигурации раскладок, Alt+Shift зависит от настройки.
- Linux: GNOME по умолчанию Super+Space; KDE Plasma позволяет назначить
  собственное переключение, включая разные политики для окна/приложения.
  Поэтому не привязывать мобильное приложение к ОС и не зашивать
  единое обязательное сочетание.
- **Никогда не отправлять Alt+Shift и Ctrl+Shift вместе**: можно дважды
  переключить разные языковые уровни либо выполнить обратную операцию.
  Один жест — ровно одно выбранное действие. Свайпы влево/вправо можно
  считать одной командой «следующая раскладка» для двух языков; при трёх
  и более раскладках направление требует отдельной настройки.
- Через вложенные Aspia и сторонние терминалы клавиши могут
  перехватываться промежуточным сеансом. Клиент не обещает, что
  переключение достигло конечного компьютера. В UI не выдавать локальное
  положение RU/EN за достоверную раскладку Windows/Linux; индикатор
  удалённой системы — источник истины.
- Локальная настройка и работа физическими скан-кодами безопаснее,
  чем незапрошенная синхронизация языка через Host. Проверить
  Windows RU/EN, GNOME (X11/Wayland), KDE Plasma, локальные терминалы,
  вложенную Aspia, пароли и несколько одновременных сеансов.
- Любые keyboard-shortcut события проходят по существующему
  пути физических KeyEvent; без новых сетевых портов и без новых
  служебных каналов. Это **план, не готовая функция**.

Источники:
https://support.microsoft.com/en-us/accessibility/windows/keyboard-shortcuts-in-windows
https://help.gnome.org/gnome-help/keyboard-shortcuts-set.html
https://docs.kde.org/stable_kf6/en/plasma-desktop/kcontrol/keyboard/layouts.html

## Цель и снятое ограничение

В рабочем контуре планируется обновление **Host, Client/Console и Android Mobile**.
Поддержка старого Host 2.7 для этой функции **не является требованием**.
Не ломать обычное подключение к старому Host без расширения, но оно не
обязано поддерживать синхронизацию раскладки.

«Mobile → Host A → Aspia Client/Console A → Host B → [Aspia B → Host C...]»
— полноценный рабочий сценарий, в том числе с несколькими участниками.
Цель: **на экране телефона показывать раскладку именно конечной Windows,
куда попадёт следующее нажатие**, а при свайпе по пробелу переключать
**раскладку только конечной Windows, с подтверждением результата**.

Не использовать слепое воспроизведение Alt+Shift / Ctrl+Shift / Win+Space
на каждом хопе. Физические USB-клавиши в desktop-сессии сохраняются; Unicode
TextEvent и вставка остаются отдельными поддерживаемыми путями.

## Что уже есть в коде проекта

**Существующий транспорт, без создания нового внешнего TCP-порта:**

- `source/proto/desktop.proto` — `DesktopExtension {name, data}`,
  двусторонне в `HostToClient.extension=5` / `ClientToHost.extension=6`,
  и `DesktopCapabilities.extensions` для объявления поддержки.
- `source/proto/desktop_extensions.proto` — формат других расширений:
  `select_screen`, `video_pause`, `screen_type`, `power_control`.
- `source/common/desktop_session_constants.{h,cc}` — имена расширений и
  `kSupportedExtensionsForManage`/`View`; `ClientSessionDesktop::readExtension`
  и `ClientDesktop::readExtension` уже маршрутизируют существующие команды.
- `source/proto/desktop_internal.proto` — `ServiceToDesktop` и
  `DesktopToService` для внутреннего Host service ⇄ desktop agent IPC.
  `source/host/desktop_session_agent.cc` работает в пользовательском
  интерактивном сеансе, имеет Win32 message window. `desktop_session_ipc.cc`,
  `desktop_session_manager.cc` и `desktop_session_proxy.cc` — путь в Host.
- `source/client/ui/desktop/desktop_widget.cc` — уже получает события
  Win32/Qt и передаёт физические USB KeyEvent. Подходящий источник состояния
  активного вложенного сеанса находится в `ClientDesktop`/окне `QtDesktopWindow`.
- Host/Client расширения передаются по существующему сеансу. Проверить в
  интеграции, что Router/Relay полностью прозрачно передают новый тип.
  Предварительно изменения Router/Relay не предполагаются.

**Чего нет:** ни рабочего `keyboard_layout_v1`, ни готового
Host-A ⇄ локальный Client-A IPC для маршрутизации вложенной раскладки.
Обычный Host IPC service ⇄ desktop agent не подключает автоматически
параллельно работающую Console/Client.

## Предлагаемый протокол

Новое согласуемое расширение `keyboard_layout_v1`, protobuf в отдельном
`source/proto/keyboard_layout.proto` (точные поля — в реализации):

- `QueryLayout`: `request_id`, `viewer_session_id`, `focus_epoch`.
- `LayoutState`: `request_id` (optional), `focus_epoch`, `generation`,
  `language_tag` (`ru-RU`, `en-US`), полное `keyboard_layout_id`/KLID,
  `source_host`, `hop_count`, `route_status` (`LOCAL`, `FORWARDED`,
  `UNKNOWN`, `LOCKED`, `UNSUPPORTED`). Передавать *идентификатор*
  раскладки и выбранного пути, **не содержимое нажатий, полей или пароль**.
- `SetLayout`: `request_id`, `focus_epoch`, целевой язык/конкретный
  KLID, `viewer_session_id`, текущий `route_id`. Это **запрос** на
  переключение в конечном контексте, не команда всем сеансам сразу.
- `SetLayoutResult`: `request_id`, `accepted`, `actual LayoutState`,
  `error`, `focus_epoch`. Мобильная клавиатура меняет вид лишь после
  подтверждения реального состояния.
- Максимум 8 вложенных переходов, ограничение размера сообщения,
  запрет циклических путей по session IDs, ограничение частоты запросов.
- Достоверный route/viewer ID назначает только локальная авторизованная
  сторона, а не берёт слепо из клиентских данных.

## Источник раскладки на Windows

Получать состояние **в интерактивном desktop agent**, а не в Session 0
службы. Узнать активный GUI-поток / hwndFocus через
`GetGUIThreadInfo` + `GetWindowThreadProcessId`, раскладку потока
через `GetKeyboardLayout(thread_id)`. Для Windows 8+ дополнительно
учитывать профиль TSF/IME; HKL — не всегда однозначный язык IME.

Отправлять изменения при смене фокуса, layout и по запросу подписчика.
Не полагаться только на `WM_INPUTLANGCHANGE`: оно приходит **окну,
в котором язык изменился**, а не гарантированно нашему hidden message
window. Для корректности нужен детектор фокуса + проверка текущего HKL
и ограниченный резервный опрос при активном desktop-сеансе. Остановить
мониторинг после закрытия/блокировки/потери прав на desktop.

Для переключения НЕ вызывать `ActivateKeyboardLayout` в процессе Host:
она меняет раскладку только самого процесса/потока Host. Следует направить
`WM_INPUTLANGCHANGEREQUEST` в актуальное окно ввода **с проверкой
прав и оконного десктопа**. Целевое приложение вправе отклонить запрос,
поэтому после изменения заново запросить `GetKeyboardLayout`, вернуть
ACK/отказ; не обещать, что каждое приложение принимает изменение.

Win32-документация:
https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getguithreadinfo
https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getkeyboardlayout
https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-inputlangchangerequest
https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-activatekeyboardlayout

## Как работает вложенный маршрут

1. Mobile подключён к Host A. Host A определяет, что **активное окно с
   фокусом — именно зарегистрированное окно Aspia Client/Console A**
   и узнаёт его локальный идентификатор desktop-сеанса.
2. Через **новый локальный ограниченный IPC bridge** (например, named pipe
   с ACL по текущему Windows logon session, PID+session+window association)
   Host A запрашивает у Client/Console A состояние удалённого сеанса B.
   Присутствие процесса Aspia само по себе недостаточно — в Console
   может быть одновременно несколько окон удалённых компьютеров.
3. Client/Console A читает подтверждённое `LayoutState` от Host B через
   штатный `DesktopExtension`. Если на B активна ещё одна Aspia,
   B повторяет шаги 1–2 рекурсивно и сообщает фактическую конечную раскладку.
4. В обратном направлении команда Mobile `SetLayout` передаётся по
   **тому же конкретному, актуальному маршруту**, не рассылается всем
   подключенным участникам и не переключает язык промежуточных машин.
5. Любая потеря фокуса, закрытие nested-window, переподключение или смена
   desktop/session делает `route_id`/`focus_epoch` недействительным:
   отменить ожидающую команду и запросить новое состояние.
6. Если активное окно не Aspia или локальный bridge не подтверждён,
   вернуть `LOCAL` с раскладкой A. Для сторонних вложенных RDP/VM
   нет права утверждать, что можно прочесть раскладку B.
7. Несколько уровней — тот же механизм, а не отдельные ветки кода для
   каждого числа хопов.

**Безопасность IPC bridge:** разрешить подключение только
авторизованным локальным компонентам Aspia+ внутри нужной пользовательской
сессии и соответствующему desktop window. Не считать любое окно с
похожим заголовком доверенным. Сама read-only метаинформация не даёт
права отправлять `SetLayout`; оно только для сеанса Desktop Manage.

## Несколько участников и честные ограничения

- Каждая **входящая сессия просмотра/управления** имеет собственные
  `viewer_session_id`, `route_id`, `focus_epoch`, `request_id`,
  `generation`. Состояния нельзя хранить одним глобальным флагом.
- Если разные сотрудники вошли в **разные RDS/Windows logon sessions**,
  для каждой отдельный desktop agent и независимый контекст раскладки.
- Если несколько сотрудников одновременно управляют **одним общим
  интерактивным рабочим столом**, в Windows общий фокус ввода. Нельзя
  гарантировать каждому независимую раскладку и независимый текстовый
  курсор без отдельного пользовательского сеанса/изоляции. UI должен
  показывать реальное текущее состояние, а опционально — владельца ввода
  и предупреждение о конкурирующем управлении.
- Для read-only сеанса можно показывать layout, но нельзя выполнять Set.
- Запрещать silently switching раскладки на login/secure desktop/UAC
  без достоверного способа и разрешения; возвращать `LOCKED/UNKNOWN`.
- Не логировать введённые символы, пароль и содержимое поля. В журнале
  допустимы только состояние/результат переключения и идентификатор сеанса.

## Мобильный интерфейс

- Подписка на `LayoutState` при открытии клавиатуры, активации окна,
  смене remote desktop и переподключении.
- Отражать подтверждённую `RU/EN` именно на активном маршруте.
  Если данных нет: `?` / `Раскладка неизвестна` и никакого
  недоказанного автоматического переключения.
- Свайп пробела отправляет `SetLayout(target=...)`, визуально показывает
  ожидание и меняет расположение букв **после ACK**; отрицательный результат
  сообщает без лишнего нажатия на клавиатуру Windows.
- Физические USB-позиции и хоткеи остаются основным транспортом.
  Unicode-ввод и вставка текста остаются явной альтернативой.
- Буквы на экране не могут гарантировать, что Windows раскладка совпадает
  с аппаратной на произвольной сторонней вложенной программе.

## Этапы разработки и контрольные тесты

1. **Direct layout telemetry:** Host A IPC+Win32 → desktop extension
   `LayoutState` → Windows Console и Android Mobile. Тесты:
   Блокнот RU↔EN, браузер, переход между двумя локальными окнами,
   Caps Lock отдельно, потеря фокуса, блокировка.
2. **Direct confirmed SetLayout:** Mobile swipe → Host → запрос
   Win32 focused-window layout → ACK actual. Проверки: непринявшее
   запрос приложение, фокус меняется между запросом и исполнением,
   несколько зрителей/один контролёр, read-only.
3. **Local nested bridge:** Console A получает layout Host B и отдаёт
   Host A *только если конкретный desktop window A находится в фокусе*.
   Тест Mobile → Host A → Console A → Host B.
4. **Recursive route:** A → B → C с depth-limit, route tokens,
   сменой активного вложенного окна и одновременной работой нескольких
   участников; нельзя загрязнять состояния между сеансами.
5. **Packaging:** обновить Host/Client/Console и Mobile согласованно,
   интеграционные тесты на реальных Windows и Android 12. Router/Relay
   оставить как есть при доказанной прозрачности extension.
   Публиковать как preview только после тестов, без утверждений о
   совместимости с произвольными RDP/VM/secure desktops.

**Это проектная спецификация. Никакая функция из неё пока не заявлена
как проверенная в APK или MSI.**
